# My D-day 서비스 구조 안내서 (비개발자용)

> 이 문서는 **개발을 몰라도** "이 서비스가 어떻게 만들어졌고, 어떻게 돌아가는지"를
> 처음부터 끝까지 이해할 수 있도록 쉬운 말과 비유로 정리한 자료입니다.

---

## 0. 한 줄 요약

**My D-day**는 중요한 날(시험, 기념일, 생일 등)까지 며칠 남았는지 세어주고,
예쁜 테마로 친구에게 공유할 수 있는 **웹사이트 + 앱(PWA)** 입니다.

- 주소: https://my-dday.vercel.app
- 휴대폰 홈 화면에 앱처럼 설치할 수 있음

---

## 1. 가장 먼저 — "웹 서비스"는 식당과 같아요 🍽️

웹 서비스를 **식당**에 비유하면 전체 구조가 한 번에 이해됩니다.

| 식당 비유 | 실제 구성요소 | 하는 일 |
|---|---|---|
| 🪑 **손님이 보는 홀**(메뉴판·테이블) | **프론트엔드** | 사용자가 눈으로 보고 누르는 화면 |
| 👨‍🍳 **주방**(요리사·조리법) | **백엔드** | 화면 뒤에서 실제 일을 처리 |
| 📦 **창고**(재료·장부) | **데이터베이스(DB)** | 회원·날짜 정보를 저장 |
| 🧾 **주문서·웨이터** | **API** | 홀(화면)과 주방(서버) 사이에서 요청을 전달 |

> 손님(사용자)이 "이거 주세요"(버튼 클릭) → 웨이터(API)가 주방(백엔드)에 전달 →
> 주방이 창고(DB)에서 재료를 꺼내 요리 → 다시 손님에게 음식(결과)이 나옵니다.

이 4가지가 웹 서비스의 핵심입니다. 아래에서 하나씩 자세히 봅니다.

## 2. 전체 그림 한 장

```
        ┌─────────────────────────────────────────────────────┐
        │                    사용자 (휴대폰/PC)                  │
        └───────────────────────┬─────────────────────────────┘
                                │ 화면 접속
                                ▼
   ┌──────────────────────────────────────────┐
   │  ① 프론트엔드 (화면)                         │   집:  Vercel
   │     - 회원가입/로그인 화면                    │
   │     - D-day 목록, 추가 화면                  │
   │     - 관리자 대시보드                         │
   └───────────────────────┬──────────────────┘
                           │ "로그인 해줘" / "목록 줘" (API 요청)
                           ▼
   ┌──────────────────────────────────────────┐
   │  ② 백엔드 (서버 = 일하는 두뇌)                │   집:  Render
   │     - 비밀번호 확인, 로그인 처리              │
   │     - D-day 저장/수정/삭제 규칙 처리          │
   │     - 메일 보내기, 권한 확인                  │
   └───────────────────────┬──────────────────┘
                           │ "이 회원 정보 꺼내줘" / "저장해줘"
                           ▼
   ┌──────────────────────────────────────────┐
   │  ③ 데이터베이스 (창고 = 저장소)               │   집:  Neon
   │     - 회원, D-day 카드, 마일스톤, 접속기록     │
   └──────────────────────────────────────────┘
```

각 박스가 **다른 회사의 무료 서비스**에 올라가 있습니다(=각자 다른 "집"에 산다).
왜 나눴는지는 4번에서 설명합니다.

## 3. 세 개의 레이어(층) 자세히 보기

### ① 프론트엔드 — "보이는 화면" 🪑

- **무엇:** 사용자가 브라우저에서 보는 모든 화면 (글자, 버튼, 색깔, 그래프)
- **무엇으로 만들었나:** HTML(뼈대) + CSS(꾸미기) + JavaScript(동작)
  - 비유: HTML=건물 골조, CSS=인테리어/페인트, JavaScript=전등 스위치·움직이는 장치
- **어디서 돌아가나:** **Vercel** 이라는 무료 호스팅
- **왜 Vercel?** 화면 파일만 올리면 알아서 전 세계 어디서나 빠르게 보여줌. 무료. 설정이 쉬움.
- **이 프로젝트의 화면들:** 로그인, 회원가입, D-day 목록, 추가/수정, 공유 페이지, 계정 설정, **관리자 대시보드**

### ② 백엔드 — "일하는 두뇌(서버)" 👨‍🍳

- **무엇:** 화면 뒤에서 실제 판단과 처리를 하는 프로그램. 흔히 "서버"라고 부름.
- **무엇으로 만들었나:** Node.js + Express (자바스크립트로 서버를 만드는 도구)
- **어디서 돌아가나:** **Render** 라는 무료 서버 호스팅
- **왜 백엔드가 따로 필요?** 중요한 판단(비밀번호 맞는지, 이 사람이 관리자인지)을
  화면에만 맡기면 누구나 조작할 수 있어 위험합니다. **믿을 수 있는 서버**가 별도로 검증해야 안전합니다.
- **하는 일 예시:**
  - 로그인 시 비밀번호가 맞는지 확인
  - "이 D-day는 이 회원 것인가?" 소유권 확인
  - 비밀번호 재설정 메일 발송
  - 관리자만 통계를 볼 수 있게 차단

### ③ 데이터베이스(DB) — "창고/장부" 📦

- **무엇:** 정보를 영구적으로 저장하는 곳. 엑셀 표(테이블)들이 모여 있다고 생각하면 쉬움.
- **무엇을 쓰나:** PostgreSQL(포스트그레스큐엘)이라는 데이터베이스
- **어디서 돌아가나:** **Neon** 이라는 무료 PostgreSQL 호스팅
- **왜 DB가 필요?** 서버는 일을 처리만 하고, 전원을 끄면 기억을 잃습니다.
  회원·날짜 같은 정보는 **꺼져도 남아야** 하므로 창고(DB)에 따로 저장합니다.
- **이 프로젝트의 표(테이블)들:**

| 표 이름 | 저장하는 것 |
|---|---|
| `users` | 회원 (이메일, 암호화된 비밀번호, 관리자 여부) |
| `ddays` | D-day 카드 (제목, 날짜, 카테고리, 메모 등) |
| `milestones` | 마일스톤 (시작일 + 100일·200일… 자동 계산) |
| `password_resets` | 비밀번호 재설정용 1회용 링크 토큰 |
| `login_logs` | 접속(로그인) 기록 — 관리자 통계용 |

## 4. 왜 세 곳으로 나눴나요? (한 곳에 다 두지 않고)

각 층은 **잘하는 회사에 따로 맡기는 게** 더 싸고 안정적이기 때문입니다.

| 층 | 맡긴 곳 | 그 회사를 고른 이유 |
|---|---|---|
| 화면 | **Vercel** | 화면 전송에 특화, 전 세계로 빠르게, 무료 |
| 서버 | **Render** | 서버를 24시간 켜서 돌려줌, 무료 플랜 유지 |
| DB | **Neon** | 안 쓰면 자동으로 잠들어 무료 한도를 아껴줌 |

> 처음엔 **Railway** 한 곳에 백엔드+DB를 함께 뒀는데, 무료 체험이 끝나 서비스가 멈췄습니다.
> 그래서 **Render(서버) + Neon(DB)** 무료 조합으로 옮겼습니다. (자세한 과정: [MIGRATION.md](MIGRATION.md))

### 💡 무료로 운영되는 이유
- Vercel: 화면 호스팅은 개인 프로젝트 무료
- Render: 15분간 아무도 안 들어오면 서버가 잠듦 → 다음 접속 때 ~50초 깨어남(=무료 유지의 대가)
- Neon: 5분간 요청 없으면 DB가 잠듦 → 접속하면 0.5초 만에 깨어남

즉 **"쓸 때만 깨어나는"** 구조라 트래픽이 적은 개인 서비스는 0원으로 돌아갑니다.

## 5. 실제로 무슨 일이 일어날까? (로그인 예시) 🔄

"로그인" 버튼 한 번에 일어나는 일을 순서대로 보면:

```
1. (화면) 사용자가 이메일/비밀번호 입력 후 [로그인] 클릭
            │
2. (화면→서버) "이 이메일/비밀번호로 로그인 시켜줘" 라고 Render 서버에 요청 (API)
            │
3. (서버→DB) 서버가 Neon 창고에서 해당 이메일의 회원을 찾음
            │
4. (서버) 저장된 암호화 비밀번호와 입력값이 일치하는지 확인
            │
5. (서버) 맞으면 "출입증"(토큰)을 발급해서 화면에 돌려줌
          + 접속 기록을 login_logs에 남김
            │
6. (화면) 출입증을 보관하고 → D-day 목록 화면으로 이동
```

이후 사용자가 목록·추가·삭제를 할 때마다 화면은 이 **출입증(토큰)**을 함께 보내고,
서버는 출입증을 확인해 "이 사람 맞네" 하고 처리합니다.

## 6. 주요 기능별 동작 요약

| 기능 | 동작 한 줄 설명 |
|---|---|
| **회원가입/로그인** | 비밀번호는 암호화해서 저장, 로그인하면 출입증(토큰) 발급 |
| **D-day 추가/수정/삭제** | 내 카드만 다룰 수 있게 서버가 소유권 확인 |
| **마일스톤** | 시작일을 넣으면 100일·200일… 날짜를 서버가 자동 계산해 저장 |
| **공유 링크** | 고유 주소를 만들어, 로그인 없이도 친구가 볼 수 있음 |
| **비밀번호 찾기** | 1회용 링크를 이메일로 보내고, 30분 안에 새 비밀번호 설정 |
| **관리자 페이지** | 관리자만 회원·접속·카드 통계를 그래프로 보고, 권한을 줄 수 있음 |

## 7. 보안 — "어떻게 안전을 지키나" 🔒

비개발자도 알아두면 좋은 핵심 4가지:

1. **비밀번호 암호화 (bcrypt)** — 비밀번호를 그대로 저장하지 않고 **되돌릴 수 없게 변환**해서 저장.
   해커가 DB를 봐도 원래 비밀번호를 알 수 없음.
2. **출입증 방식 (JWT 토큰)** — 로그인하면 위조 불가능한 출입증을 받아, 매 요청마다 신분을 증명.
3. **권한은 서버가 매번 확인** — "관리자인지"를 화면 말이 아니라 **서버가 DB로 직접** 확인 → 조작 불가.
4. **요청 횟수 제한 (rate limit)** — 비밀번호를 무한정 시도하는 공격을 막기 위해 횟수를 제한.

## 8. 개발의 시작과 끝 — "코드가 어떻게 서비스가 되나" 🚀

개발자가 코드를 고치면, 사용자에게 반영되기까지의 흐름입니다.

```
1. 코드 작성/수정 (내 컴퓨터)
        │
2. GitHub에 올림 (git push)  ← GitHub = 코드 보관 창고 + 변경 이력 기록
        │
3. 자동 배포 트리거
   ├─ 화면이 바뀌면 → Vercel이 자동으로 새 화면 배포
   └─ 서버가 바뀌면 → Render가 자동으로 새 서버 배포
        │
4. 1~3분 뒤 사용자에게 반영 ✅
```

- **GitHub**: 코드의 "구글 드라이브 + 타임머신". 누가 언제 무엇을 바꿨는지 다 기록됨.
- **자동 배포**: GitHub에 올리기만 하면 Vercel·Render가 알아서 최신 버전으로 갱신.
- 그래서 개발자는 "코드 수정 → git push" 만 하면 끝입니다.

## 9. 폴더 구조 (이 프로젝트의 실제 모습)

```
my-dday/
├─ frontend/          ← ① 화면 (Vercel이 가져감)
│   ├─ *.html           각 페이지 (로그인, 목록, 관리자 등)
│   ├─ css/             꾸미기(디자인)
│   └─ js/              화면 동작 + 서버에 요청하는 코드(api.js)
│
├─ backend/           ← ② 서버 (Render가 가져감)
│   └─ src/
│       ├─ routes/      기능별 처리(로그인, D-day, 공유, 관리자)
│       ├─ middleware/  공통 검문소(인증 확인, 관리자 확인)
│       ├─ migrations/  DB 표 만드는 설계도(SQL)
│       └─ server.js    서버 켜는 시작점
│
└─ docs/              ← 📄 문서 (지금 보는 이 파일 포함)
    ├─ PRD.md           무엇을 만들지(기능 요구사항)
    ├─ TRD.md           어떻게 만들지(기술 상세)
    ├─ CHANGELOG.md     무엇이 바뀌었는지(변경 이력)
    └─ ARCHITECTURE.md  구조 안내(이 문서)
```

## 10. 용어 사전 (자주 나오는 말) 📖

| 용어 | 쉬운 뜻 |
|---|---|
| **프론트엔드** | 사용자가 보는 화면 (홀) |
| **백엔드 / 서버** | 화면 뒤에서 일하는 프로그램 (주방) |
| **데이터베이스(DB)** | 정보를 저장하는 창고 |
| **API** | 화면과 서버가 주고받는 약속된 요청/응답 (주문서) |
| **배포(deploy)** | 만든 것을 실제 인터넷에 올려 사용 가능하게 함 |
| **호스팅** | 화면·서버·DB를 24시간 돌려주는 임대 서비스 |
| **토큰(JWT)** | 로그인 후 받는 위조 불가 출입증 |
| **환경변수** | 비밀번호·접속주소 같은 민감한 설정값 (코드에 직접 안 쓰고 따로 보관) |
| **마이그레이션** | DB에 표를 만들거나 바꾸는 작업 |
| **PWA** | 웹사이트를 앱처럼 홈 화면에 설치하는 기술 |
| **콜드 스타트** | 잠들어 있던 무료 서버가 깨어나는 데 걸리는 잠깐의 지연 |
| **Git / GitHub** | 코드 보관 + 변경 이력 관리 도구/사이트 |

## 11. 한눈에 정리

- **화면(Vercel)** · **서버(Render)** · **창고(Neon)** 세 층으로 이루어진 웹 서비스
- 사용자 클릭 → 화면이 서버에 요청 → 서버가 창고에서 꺼내 처리 → 다시 화면으로
- 코드를 **GitHub에 올리면 자동으로 배포**되어 사용자에게 반영
- 비밀번호 암호화·출입증·권한 확인으로 **안전**하게, 세 곳 모두 **무료**로 운영

> 더 알고 싶다면: 기능은 [PRD.md](PRD.md), 기술 상세는 [TRD.md](TRD.md),
> 이전 과정은 [MIGRATION.md](MIGRATION.md), 변경 이력은 [CHANGELOG.md](CHANGELOG.md)를 보세요.
